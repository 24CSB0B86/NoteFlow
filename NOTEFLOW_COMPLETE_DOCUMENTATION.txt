1. PROJECT OVERVIEW & VISION
================================================================================

NoteFlow is an AI-powered, collaborative note-sharing and academic resource
management platform designed for university students and professors. It solves
the problem of fragmented, unorganised study materials by providing a single
private classroom environment where professors and students can upload, annotate,
discuss, and review academic content.

The platform's core differentiators are:
  - Collaborative PDF annotation with real-time heatmaps showing which sections
    are most studied by the class.
  - A gamified Karma + Badge system that rewards contribution quality.
  - A Bounty Board where students/professors can post rewards for specific notes.
  - An integrated AI Chatbot (GPT-3.5-turbo + FAQ fallback) for platform help.
  - Dedicated Exam Sections with AI-generated revision tests from uploaded PDFs.
  - A Professor Analytics Dashboard for class engagement insights.
  - Full Role-Based Access Control (RBAC) separating student and professor flows.

The project was built as a Software Engineering course project and follows a
monorepo structure with a React frontend (Vite) and a Node.js/Express backend,
connected to a PostgreSQL database (Neon DB) and Supabase for file storage.

4. SYSTEM ARCHITECTURE
================================================================================

The system follows a classic three-tier architecture:

  ┌─────────────────────────────────────────────────────────────────┐
  │                         USER'S BROWSER                          │
  │   React 18 SPA (Vite) — runs at http://localhost:5173 (dev)    │
  │         or https://noteflow.vercel.app (production)             │
  └───────────────────────────┬─────────────────────────────────────┘
                              │ HTTPS (JSON REST API calls via Axios)
                              ▼
  ┌─────────────────────────────────────────────────────────────────┐
  │               EXPRESS 4 BACKEND API SERVER                      │
  │   Runs at http://localhost:3001 (dev) / Render.com (prod)      │
  │                                                                 │
  │   Middleware Stack:                                             │
  │     helmet → cors → json parser → HTTPS redirect →             │
  │     request logger → morgan → routes                           │
  │                                                                 │
  │   Route Modules (13 total):                                     │
  │     /api/auth, /api/classrooms, /api/syllabus,                 │
  │     /api/resources, /api/highlights, /api/discussions,          │
  │     /api/karma, /api/bounties, /api/analytics,                 │
  │     /api/verify, /api/moderate, /api/chat, /api/exam           │
  └───┬─────────────────────┬──────────────────────┬───────────────┘
      │                     │                      │
      ▼                     ▼                      ▼
  ┌──────────┐      ┌──────────────┐      ┌──────────────────┐
  │ Neon DB  │      │  Supabase    │      │  OpenAI API      │
  │PostgreSQL│      │  Storage     │      │  GPT-3.5-turbo   │
  │ (SQL)    │      │  (S3 files)  │      │  (chatbot+tests) │
  └──────────┘      └──────────────┘      └──────────────────┘

AUTHENTICATION FLOW:
  1. User signs up / logs in via Supabase Auth (frontend).
  2. Supabase returns a JWT access token.
  3. Frontend stores token in Supabase session, attaches to every API request
     as "Authorization: Bearer <token>".
  4. Backend auth.middleware.js verifies the token via supabaseAdmin.auth.getUser().
  5. If valid, it fetches the user's full profile (id, email, full_name, role)
     from the local PostgreSQL users table and attaches to req.user.
  6. Role middleware (role.middleware.js) then checks req.user.role === 'professor'
     for professor-only endpoints.

6. DATABASE SCHEMA (ALL TABLES)
================================================================================

NoteFlow uses PostgreSQL (Neon DB). All tables use UUID primary keys generated
via uuid_generate_v4(). All tables with updated_at have an auto-trigger.

────────────────────────────────────────
TABLE: users
────────────────────────────────────────
  id               UUID PK DEFAULT uuid_generate_v4()
  email            TEXT UNIQUE NOT NULL
  full_name        TEXT NOT NULL
  role             TEXT NOT NULL CHECK (role IN ('professor', 'student'))
  university_email TEXT
  avatar_url       TEXT
  is_flagged       BOOLEAN DEFAULT FALSE      (added in migration 006)
  is_restricted    BOOLEAN DEFAULT FALSE      (added in migration 006)
  flag_reason      TEXT                       (added in migration 006)
  created_at       TIMESTAMPTZ DEFAULT NOW()
  updated_at       TIMESTAMPTZ DEFAULT NOW()

  Indexes: idx_users_email, idx_users_role

────────────────────────────────────────
TABLE: classrooms
────────────────────────────────────────
  id            UUID PK
  name          TEXT NOT NULL
  section       TEXT NOT NULL
  professor_id  UUID REFERENCES users(id) ON DELETE CASCADE
  invite_code   TEXT UNIQUE NOT NULL (6-character code)
  description   TEXT
  created_at    TIMESTAMPTZ DEFAULT NOW()

  Indexes: idx_classrooms_professor, idx_classrooms_invite_code (UNIQUE)

────────────────────────────────────────
TABLE: classroom_members
────────────────────────────────────────
  id            UUID PK
  classroom_id  UUID REFERENCES classrooms(id) ON DELETE CASCADE
  user_id       UUID REFERENCES users(id) ON DELETE CASCADE
  joined_at     TIMESTAMPTZ DEFAULT NOW()
  UNIQUE (classroom_id, user_id)

  Indexes: idx_members_classroom, idx_members_user

────────────────────────────────────────
TABLE: syllabus
────────────────────────────────────────
  id            UUID PK
  classroom_id  UUID REFERENCES classrooms(id) ON DELETE CASCADE (UNIQUE)
  created_by    UUID REFERENCES users(id)
  updated_at    TIMESTAMPTZ DEFAULT NOW()

────────────────────────────────────────
TABLE: syllabus_nodes
────────────────────────────────────────
  id            UUID PK
  syllabus_id   UUID REFERENCES syllabus(id) ON DELETE CASCADE
  parent_id     UUID REFERENCES syllabus_nodes(id) ON DELETE CASCADE (self-ref)
  node_type     TEXT CHECK (node_type IN ('unit', 'topic', 'subtopic'))
  title         TEXT NOT NULL
  order_index   INT DEFAULT 0
  has_resources BOOLEAN DEFAULT FALSE (auto-updated by trigger)
  created_at    TIMESTAMPTZ DEFAULT NOW()

  Indexes: idx_nodes_syllabus, idx_nodes_parent

────────────────────────────────────────
TABLE: resources
────────────────────────────────────────
  id               UUID PK
  syllabus_node_id UUID REFERENCES syllabus_nodes(id) ON DELETE CASCADE
  classroom_id     UUID REFERENCES classrooms(id) ON DELETE CASCADE
  uploader_id      UUID REFERENCES users(id) ON DELETE CASCADE
  file_name        TEXT NOT NULL
  file_url         TEXT NOT NULL (Supabase Storage URL)
  file_type        TEXT
  metadata         JSONB DEFAULT '{}' (title, description, tags, thumbnail_url, etc.)
  version          INT DEFAULT 1
  is_verified      BOOLEAN DEFAULT FALSE
  is_deleted       BOOLEAN DEFAULT FALSE      (added migration 006)
  deleted_at       TIMESTAMPTZ                (added migration 006)
  deleted_by       UUID REFERENCES users(id)  (added migration 006)
  view_count       INT DEFAULT 0              (added migration 006)
  created_at       TIMESTAMPTZ DEFAULT NOW()

  Indexes: idx_resources_node, idx_resources_classroom, idx_resources_uploader
  Trigger: trg_enqueue_verification — auto-adds to verification_queue on insert
  Trigger: trg_update_has_resources_insert/delete — updates has_resources on node

────────────────────────────────────────
TABLE: highlights
────────────────────────────────────────
  id            UUID PK
  resource_id   UUID REFERENCES resources(id) ON DELETE CASCADE
  user_id       UUID REFERENCES users(id) ON DELETE CASCADE
  page_number   INT NOT NULL
  coordinates   JSONB NOT NULL  { x1, y1, x2, y2 } normalized 0-1 relative to page
  text_content  TEXT (the actual selected text)
  color         TEXT DEFAULT '#facc15' (yellow)
  created_at    TIMESTAMPTZ DEFAULT NOW()

  Indexes: idx_highlights_resource, idx_highlights_resource_page, idx_highlights_user

────────────────────────────────────────
TABLE: heatmap_data
────────────────────────────────────────
  id               UUID PK
  resource_id      UUID REFERENCES resources(id) ON DELETE CASCADE
  page_number      INT NOT NULL
  aggregated_zones JSONB DEFAULT '[]' — array of { x, y, width, height, intensity 0-100 }
  last_calculated  TIMESTAMPTZ DEFAULT NOW()
  UNIQUE (resource_id, page_number)

  Indexes: idx_heatmap_resource

────────────────────────────────────────
TABLE: discussions
────────────────────────────────────────
  id           UUID PK
  resource_id  UUID REFERENCES resources(id) ON DELETE CASCADE
  parent_id    UUID REFERENCES discussions(id) ON DELETE CASCADE (threading)
  user_id      UUID REFERENCES users(id) ON DELETE CASCADE
  content      TEXT NOT NULL
  page_number  INT (which PDF page the discussion is anchored to)
  position     JSONB  { x, y } for anchored position on page
  resolved     BOOLEAN DEFAULT FALSE
  pinned       BOOLEAN DEFAULT FALSE
  is_deleted   BOOLEAN DEFAULT FALSE (added migration 006)
  is_helpful   BOOLEAN DEFAULT FALSE (added migration 006)
  created_at   TIMESTAMPTZ DEFAULT NOW()
  updated_at   TIMESTAMPTZ DEFAULT NOW()

  Indexes: idx_discussions_resource, idx_discussions_parent,
           idx_discussions_user, idx_discussions_page

────────────────────────────────────────
TABLE: discussion_votes
────────────────────────────────────────
  id             UUID PK
  discussion_id  UUID REFERENCES discussions(id) ON DELETE CASCADE
  user_id        UUID REFERENCES users(id) ON DELETE CASCADE
  vote_type      TEXT CHECK (vote_type IN ('up', 'down'))
  created_at     TIMESTAMPTZ DEFAULT NOW()
  UNIQUE (discussion_id, user_id) — one vote per user per discussion

────────────────────────────────────────
TABLE: badges
────────────────────────────────────────
  id          UUID PK
  name        TEXT UNIQUE NOT NULL
  description TEXT NOT NULL
  icon        TEXT DEFAULT '🏅'
  rarity      TEXT CHECK (rarity IN ('common', 'rare', 'legendary'))
  criteria    JSONB  { "type": "upload_count", "threshold": 10 }
  created_at  TIMESTAMPTZ DEFAULT NOW()

  Pre-seeded badges (11 total):
    - Getting Started  (common)    — Upload 1 resource
    - Contributor      (common)    — Upload 10 resources
    - Knowledge Sharer (rare)      — Upload 50 resources
    - Helper           (common)    — Fulfill 1 bounty
    - Bounty Hunter    (rare)      — Fulfill 5 bounties
    - Legendary Hunter (legendary) — Fulfill 20 bounties
    - Certified        (rare)      — Have 1 professor-verified resource
    - Popular          (rare)      — Receive 50 upvotes
    - Wise One         (legendary) — 10 discussions marked helpful
    - Streak Master    (common)    — 7-day login streak
    - Legend           (legendary) — Reach Level 5 (1000+ karma)

────────────────────────────────────────
TABLE: user_karma
────────────────────────────────────────
  id            UUID PK
  user_id       UUID REFERENCES users(id) ON DELETE CASCADE (UNIQUE)
  total_points  INT DEFAULT 0
  level         INT DEFAULT 1
  last_login    DATE
  login_streak  INT DEFAULT 0
  created_at    TIMESTAMPTZ DEFAULT NOW()
  updated_at    TIMESTAMPTZ DEFAULT NOW()

  Indexes: idx_user_karma_user, idx_user_karma_points DESC

────────────────────────────────────────
TABLE: karma_transactions
────────────────────────────────────────
  id           UUID PK
  user_id      UUID REFERENCES users(id) ON DELETE CASCADE
  points       INT NOT NULL (can be negative for penalties)
  action_type  TEXT CHECK (action_type IN (
                 'upload', 'upvote', 'downvote', 'bounty_fulfill',
                 'bounty_create', 'discussion_helpful', 'login_streak',
                 'professor_verify', 'spam_penalty', 'badge_bonus',
                 'manual_adjustment'))
  reference_id UUID (resource_id, bounty_id, discussion_id, etc.)
  description  TEXT
  created_at   TIMESTAMPTZ DEFAULT NOW()

  Append-only immutable ledger. Never deleted or updated.
  Indexes: idx_karma_tx_user, idx_karma_tx_created DESC, idx_karma_tx_action

────────────────────────────────────────
TABLE: user_badges
────────────────────────────────────────
  id         UUID PK
  user_id    UUID REFERENCES users(id) ON DELETE CASCADE
  badge_id   UUID REFERENCES badges(id) ON DELETE CASCADE
  earned_at  TIMESTAMPTZ DEFAULT NOW()
  UNIQUE (user_id, badge_id)

7.1 ENTRY POINT (server/src/index.js)
--------------------------------------
The Express application is bootstrapped here. All middleware is applied in order:

  1. helmet()         — Sets HTTP security headers (CSP, HSTS, X-Frame-Options,
                        etc.). CSP is configured to allow Supabase, OpenAI,
                        Google Fonts, and PDF.js.
  2. cors()           — Allows requests from localhost:5173, 5174, 5175 (dev)
                        and the CLIENT_URL env var (production Vercel URL).
  3. express.json()   — Parses JSON request bodies (limit: 10MB).
  4. urlencoded()     — Parses URL-encoded bodies (limit: 10MB).
  5. HTTPS redirect   — In production, redirects HTTP → HTTPS.
  6. Request logger   — Custom middleware that logs "[API CALL ⚡] METHOD /path".
  7. morgan('dev')    — Standard HTTP request logger (status, timing, etc.).

All 13 route modules are then mounted at their respective /api/* paths.

A health check endpoint at GET /api/health returns:
  { status: 'ok', timestamp, env, ai: 'openai' | 'rule-based' }

Global 404 and 500 error handlers are defined after all routes.

The server listens on PORT env var (default 3001).

7.2 MIDDLEWARE
--------------
Three middleware files:

  auth.middleware.js (authenticate)
  ----------------------------------
  - Reads "Authorization: Bearer <token>" from request headers.
  - Validates the token against Supabase using supabaseAdmin.auth.getUser().
  - Fetches the user's DB profile (id, email, full_name, role) from PostgreSQL.
  - Attaches req.user and req.token.
  - Returns 401 for missing, null, or invalid tokens.
  - Guards: All protected routes use this middleware.

  role.middleware.js (requireRole)
  ----------------------------------
  - Accepts a role string ('professor') as argument.
  - Checks req.user.role === required role.
  - Returns 403 Forbidden if role doesn't match.
  - Used on: classroom creation, resource verification, moderation, analytics.

  rateLimit.middleware.js
  -----------------------
  - Auth endpoints: 20 requests per 15 minutes per IP.
  - Chat endpoints: 30 messages per minute per user.
  - Prevents brute-force attacks and API abuse.

7.4 CONTROLLERS (11 Controller Files)
--------------------------------------
Each controller exports async handler functions used by the routes.
Key controllers explained:

  auth.controller.js
  - signUp(): Creates Supabase Auth user, then inserts row in users table.
  - login(): Authenticates via Supabase, creates user_karma row if missing,
             records login streak, returns session token.
  - getMe(): Returns req.user (already populated by middleware).

  resource.controller.js
  - uploadResource(): Uses Multer for multipart parsing. Validates file type
    and size. Calls fileProcessor.js for thumbnail and compression. Uploads
    to Supabase Storage. Inserts DB record. Awards karma via karmaEngine.
  - getResourceViewUrl(): Generates signed/public URL for viewing.
  - deleteResource(): Soft-deletes by setting is_deleted = TRUE.

  highlight.controller.js
  - saveHighlight(): Saves highlight coordinates (normalized 0-1), page number,
    and text content. Triggers heatmap recalculation via heatmapService.
  - getHeatmap(): Returns aggregated heatmap_data for a resource page.

  exam.controller.js
  - generateTest(): Calls aiService.generateTestFromContext() with extracted
    text from uploaded exam resources. AI returns a structured JSON test which
    is saved to revision_tests and test_questions tables.
  - submitAttempt(): Grades answers by comparing to correct_opt for each
    question. Calculates percentage. Awards karma based on score (see section 9).

  analytics.controller.js
  - getClassroomAnalytics(): Aggregates data from analytics_events,
    resources, discussions, karma_transactions, and user_karma tables.
    Returns engagement timelines, resource quality scores, heatmap insights,
    student activity rankings, and bounty statistics.

  bounty.controller.js
  - createBounty(): Creates bounty, optionally links to syllabus node.
  - claimBounty(): Updates status to 'claimed', sets claimer_id and claimed_at.
  - submitBounty(): Creates bounty_submission record with uploaded resource.
  - reviewBounty(): Professor approves → awards karma to fulfiller, updates
    bounty status to 'fulfilled'. Reject → sends rejection notification.

7.5 SERVICES (5 Service Modules)
---------------------------------
  aiService.js
  - getChatResponse(userMessage, history, contextText):
      If OPENAI_API_KEY is set: calls GPT-3.5-turbo via OpenAI SDK.
      Sends system prompt (NoteFlow context) + last 6 turns + user message.
      Falls back to rule-based FAQ if OpenAI fails or key is missing.
  - generateTestFromContext(prompt, contextText):
      Sends PDF text as context to GPT-3.5-turbo.
      Instructs model to return strict JSON matching the test schema.
      Temperature 0.5 for accuracy. Max 3000 tokens. Strips markdown wrappers.
  - FAQ_RULES: 10 rule patterns covering join, upload, karma, heatmap,
      bounty, password, discussion, professor, download, and search topics.

  karmaEngine.js
  - KARMA_POINTS table:
      upload: +10, upvote: +2, downvote: -1, bounty_fulfill: +20,
      discussion_helpful: +5, login_streak: +1, professor_verify: +15,
      spam_penalty: -50
  - LEVELS:
      Level 1 Novice (0-100), Level 2 Contributor (101-300),
      Level 3 Expert (301-600), Level 4 Master (601-1000),
      Level 5 Legend (1001+)
  - awardKarma(): Inserts karma_transaction, updates user_karma total,
      recalculates level, checks and awards badges, logs level-ups.
  - checkAndAwardBadges(): Queries all badges, checks BADGE_CHECKERS for
      each unearned badge, inserts user_badges row, creates notification.
  - recordLoginStreak(): Checks last_login date, increments or resets streak,
      awards login_streak karma.
  - createNotification(): Inserts notification row, optionally sends email
      for badge_earned, bounty_approved, professor_verify events.

  emailService.js
  - sendNotificationEmail(): Uses Nodemailer with Gmail App Password or SMTP.
    Sends HTML emails for bounty claims, resource approvals, badge unlocks.

  fileProcessor.js
  - validateFile(): Checks MIME type against allowed types (PDF, DOCX, PPTX, TXT).
  - generateThumbnail(): Uses sharp to create a JPEG preview image.
  - compressFile(): Compresses large files for storage efficiency.
  - extractText(): Extracts raw text from PDF/document for AI test generation.

  heatmapService.js
  - calculateHeatmap(resourceId, pageNumber): Fetches all highlights for
    a resource page. Aggregates overlapping regions. Normalises intensity (0-100).
    Upserts result into heatmap_data table.
  - Gradient mapping: 1-5 overlapping highlights = light yellow,
    6-15 = orange, 16+ = red (hot spot).

9. CORE FEATURES — IN-DEPTH EXPLANATION
================================================================================

9.1 AUTHENTICATION & ROLE-BASED ACCESS CONTROL
-----------------------------------------------
NoteFlow uses a dual-layer auth system:
  Layer 1: Supabase Auth handles the actual JWT token creation and validation.
           Students/professors sign up with email + password via Supabase.
           Supabase returns an access_token (JWT) and refresh_token.
  Layer 2: NoteFlow's own users table stores the role, full_name, and profile info.
           On every API call, auth.middleware.js verifies the Supabase JWT and
           cross-references with the local users table.

Roles:
  - "student"   : Can join classrooms, upload resources (pending approval),
                  highlight PDFs, post discussions, take tests, claim bounties.
  - "professor" : Can create classrooms, auto-approve uploads, verify resources,
                  view analytics, moderate content, create exam sections,
                  generate AI tests, approve/reject bounty submissions.

9.2 CLASSROOMS
--------------
Classrooms are private spaces created by professors. Each classroom has:
  - A unique 6-character alphanumeric invite code.
  - A name, section (e.g., "Section A"), and optional description.
  - A professor (owner) with full permissions.
  - A list of enrolled students (classroom_members table).

Flow:
  Professor: Clicks "Create Classroom" → fills form → API call → classroom
  created in DB → unique invite code generated (nanoid) → professor can
  copy/share code with students.

  Student: Clicks "Join Classroom" → enters 6-char code → API validates code
  exists in classrooms table → inserts into classroom_members → student
  immediately sees classroom in their list.

9.3 SYLLABUS TREE
-----------------
Each classroom has exactly one syllabus (one-to-one relationship).
The syllabus contains syllabus_nodes organised as a tree:
  - Units (top-level, e.g., "Unit 1: Introduction to Algorithms")
  - Topics (children of units, e.g., "1.1 Sorting Algorithms")
  - Subtopics (children of topics, e.g., "1.1.1 Merge Sort")

Professors create and manage the syllabus tree via the classroom Resources tab.
Students browse the tree to find relevant resources.
Resources are attached to specific syllabus_nodes.
The has_resources flag on each node is auto-updated by DB trigger.
The tree supports drag-and-drop reordering (order_index field).

9.4 RESOURCE MANAGEMENT & FILE UPLOADS
---------------------------------------
Supported file types: PDF, DOCX, PPTX, TXT
Maximum file size: 100MB (Supabase free tier: 50MB per file)

Upload flow:
  1. User clicks "Upload Resource" → drag-and-drop file area appears (react-dropzone).
  2. Frontend sends multipart/form-data to POST /api/resources.
  3. Multer parses the file in memory.
  4. fileProcessor.js validates file type (MIME check) and size.
  5. File is uploaded to Supabase Storage bucket "resources".
  6. Thumbnail is generated (sharp) and uploaded as a separate file.
  7. File metadata (title, description, tags, thumbnail_url, file_url) is
     saved to the resources table.
  8. Resource is automatically added to verification_queue (DB trigger).
  9. Karma points (+10) are awarded to the uploader.
  10. If professor uploaded → is_verified = TRUE immediately.
      If student uploaded → is_verified = FALSE, shows "Pending Verification" badge.

Versioning: resources.version INT is incremented when a resource is replaced.

9.5 PDF VIEWER & HIGHLIGHTS
-----------------------------
When a user clicks a resource, they go to ResourceViewerPage.
The PDF is rendered using react-pdf (wrapper around Mozilla PDF.js).
Pages are lazy-loaded for performance.

Highlighting:
  - User selects text with mouse → highlight toolbar appears.
  - User picks a color (yellow, pink, blue, green).
  - On save, frontend sends: { resource_id, page_number, coordinates {x1,y1,x2,y2},
    text_content, color } to POST /api/highlights.
  - Coordinates are stored normalized (0-1 relative to page dimensions) for
    resolution-independence.
  - Highlights are rendered as colored overlays on the PDF page.
  - Hovering a highlight shows who highlighted it and when.

9.6 COLLABORATIVE HEATMAPS
---------------------------
The heatmap is a visual density map of all highlights by all classroom members.

How it works:
  1. Every time a highlight is saved, heatmapService.calculateHeatmap() is called.
  2. All highlights for that resource page are fetched from the highlights table.
  3. Overlapping coordinate regions are aggregated.
  4. Intensity is normalized: 1-5 overlaps = low (yellow), 6-15 = medium (orange),
     16+ = high (red).
  5. Result is upserted into heatmap_data as aggregated_zones JSON array.
  6. The result is cached per (resource_id, page_number).

On the viewer:
  - User clicks "Show Heatmap" toggle.
  - Frontend fetches heatmap_data from GET /api/highlights/heatmap/:resourceId.
  - Heatmap zones are rendered as semi-transparent colored rectangles on a
    canvas layer overlaying the PDF page.
  - Tooltip on hover shows: "X students highlighted this area".
  - Toggle off hides the overlay without closing the PDF.

Business rules:
  - Heatmap includes ONLY highlights from classroom members.
  - Updates within ~5 seconds of a new highlight being saved.
  - The overlay is semi-transparent to not obscure the underlying text.

9.7 THREADED DISCUSSIONS
-------------------------
Discussions are comments anchored to specific highlights or pages on a PDF.

Posting a discussion:
  1. User selects text or clicks a page location.
  2. Popup shows "Discuss" button.
  3. User types a comment → POST /api/discussions.
  4. Discussion is stored with resource_id, page_number, position (x,y),
     parent_id = NULL for top-level threads.

Replies:
  - Other users can reply by posting with parent_id set to the original discussion.
  - This creates a threaded tree structure.

Voting:
  - PATCH /api/discussions/:id/vote with { vote_type: 'up' | 'down' }.
  - Each user can vote once per discussion (UNIQUE constraint).
  - +2 karma for original poster on upvote, -1 on downvote.
  - Professor can mark a discussion as "helpful" (is_helpful = TRUE) → +5 karma.

Moderation:
  - Professors can soft-delete discussions (is_deleted = TRUE).
  - Deleted discussions are hidden from students but logged in moderation_logs.

9.8 KARMA & GAMIFICATION SYSTEM
---------------------------------
Karma is NoteFlow's reputation and engagement system.

Points awarded:
  Action                       Points
  --------------------------   ------
  Upload a resource            +10
  Resource upvoted             +2
  Resource downvoted           -1
  Bounty fulfilled (approved)  +20
  Discussion marked helpful    +5
  Daily login streak           +1 per day
  Professor verifies resource  +15
  Spam penalty                 -50

Level Thresholds:
  Level 1: Novice       (0–100 pts)
  Level 2: Contributor  (101–300 pts)
  Level 3: Expert       (301–600 pts)
  Level 4: Master       (601–1000 pts)
  Level 5: Legend       (1001+ pts)

When a user levels up:
  - karmaEngine.js detects the new level > old level.
  - A level-up notification is created.
  - On the frontend, a confetti animation (react-confetti) plays.
  - The progress bar on the profile page fills toward the next level.

Login Streak:
  - recordLoginStreak() checks if last_login was yesterday.
  - If yes: streak incremented by 1.
  - If not: streak resets to 1.
  - If already logged in today: no change.
  - At streak 7: "Streak Master" badge is awarded.

Badge System:
  - After every karma award, checkAndAwardBadges() runs.
  - It checks all 11 badge criteria against the user's current stats.
  - Any newly eligible badge is inserted into user_badges.
  - A notification is created and optionally an email is sent.

9.9 BOUNTY BOARD
-----------------
The Bounty Board enables resource crowdsourcing within a classroom.

Creating a Bounty:
  - Any classroom member (student or professor) can create a bounty.
  - Fields: title, description, karma reward (points_reward), urgency flag,
    optional link to a specific syllabus node, optional expiry date.
  - Bounty starts with status = 'open'.

Claiming a Bounty:
  - A student clicks "Claim" on an open bounty.
  - Status changes to 'claimed', claimer_id and claimed_at are set.
  - No other student can claim a bounty already claimed.

Submitting Fulfillment:
  - The claimer uploads a resource file as fulfillment.
  - A bounty_submissions record is created (status = 'pending').
  - The bounty requester (or professor) is notified.

Approving/Rejecting:
  - Professor (or bounty creator) clicks Approve or Reject.
  - Approve: bounty status → 'fulfilled'. Fulfiller earns bounty.points_reward karma.
  - Reject: bounty status → 'open' again. Rejection reason sent as notification.

Bounty statuses: open → claimed → fulfilled | rejected → open (on rejection)
Also: 'closed' (manually closed), 'expired' (past expires_at date).

9.10 AI CHATBOT
----------------
The AI chatbot is a floating widget (bottom-right of all authenticated pages).

Two modes:
  Mode 1 — OpenAI Mode (if OPENAI_API_KEY is configured):
    - Uses GPT-3.5-turbo model.
    - System prompt: NoteFlow platform context (features, rules, personality).
    - Keeps last 6 turns of conversation for context window management.
    - Max 500 tokens per response. Temperature 0.7 for conversational tone.
    - Context injection: user's current classroom info can be prepended.

  Mode 2 — Rule-Based FAQ Fallback (works without any API key):
    - 10 pattern-matching rules covering common questions.
    - Topics: joining classrooms, uploading resources, karma, heatmaps,
      bounties, password reset, discussions, professor features, downloads, search.
    - Matches by checking if any keyword from the pattern list appears in
      the user's message (case-insensitive).
    - If no pattern matches: shows default help message with category list.

Chat history:
  - All messages (user + assistant) are stored in chat_messages table.
  - GET /api/chat/history returns paginated history.
  - DELETE /api/chat/history clears all history for the user.
  - PATCH /api/chat/:id/rate lets users rate each bot message (👍/👎).

9.11 EXAM SECTIONS & REVISION TESTS
--------------------------------------
Each classroom has dedicated Midterm and Endterm exam sections.

Exam Resources (Use Case 4.0):
  Three resource types:
    - PYQ (Previous Year Question Papers)
    - Important Questions (curated list of likely exam questions)
    - Quick Revision (condensed notes/cheat sheets)

  Student upload flow:
    1. Student uploads file + selects resource_type + enters year and description.
    2. Resource saved with status = 'pending'.
    3. Professor receives notification to review.
    4. Professor approves → status = 'approved', resource visible to all students,
       student earns +15 karma.
    5. Professor rejects → status = 'rejected', student gets rejection reason.
  
  Professor upload: Auto-approved. Instantly visible to all students.

AI-Generated Revision Tests (Use Case 5.0):
  1. Professor selects exam resource(s) (PDF files).
  2. fileProcessor.extractText() pulls text from the PDFs.
  3. Professor sets: question count, difficulty, topic focus.
  4. POST /api/exam/sections/:sectionId/tests/generate is called.
  5. aiService.generateTestFromContext() sends extracted text to GPT-3.5-turbo.
  6. AI returns strict JSON: { title, description, duration_mins, topics_covered,
     questions: [{ question, options: [{id,text}x4], correct_opt, explanation }] }
  7. Test and questions are saved to revision_tests and test_questions tables.
  8. Test becomes visible in the Revision Tests tab.

Taking a Test:
  1. Student clicks test → sees: title, duration, question count, topics.
  2. Clicks "Start Test" → timer begins (server time synced).
  3. Questions shown one at a time, student selects A/B/C/D.
  4. Navigation: Next/Previous/Question map panel.
  5. Auto-save every 30 seconds (prevents data loss).
  6. Submit or timer expires → answers sent to PATCH /api/exam/attempts/:id/submit.
  7. Backend grades: counts correct answers, calculates percentage.
  8. Karma awarded based on score:
       90-100% → +20 pts, 75-89% → +15 pts, 60-74% → +10 pts, <60% → +5 pts.
  9. Results page: score, correct/incorrect breakdown, explanations per question.

Test rules:
  - Max 3 attempts per student per test.
  - Best score is recorded for leaderboard.
  - Questions randomized on each attempt (anti-cheating).
  - Students cannot view correct answers until submission.

9.12 PROFESSOR ANALYTICS DASHBOARD
-------------------------------------
Accessible at /classrooms/:classroomId/professor (professors only).

Data visualized:
  - Engagement Over Time: Line chart showing daily/weekly counts of views,
    downloads, uploads, discussions, and highlights. Powered by Recharts.
  - Resource Quality Scores: Bar chart ranking all classroom resources by a
    composite quality score (views + downloads + discussions + highlights).
  - Student Activity Table: Per-student breakdown of activity metrics.
  - Heatmap Insights: Which resources and which pages have the most highlights.
  - Bounty Statistics: Open vs. fulfilled vs. expired bounties.
  - Verification Queue: List of student-uploaded resources pending review.
    Professor clicks Approve/Reject directly from this panel.
  - Moderation Panel: Flag users, restrict users, delete discussions.

All data sourced from analytics_events table and aggregated queries across

9.13 MODERATION & VERIFICATION
--------------------------------
Verification (Resource Quality Control):
  - Every uploaded resource is auto-enqueued in verification_queue (DB trigger).
  - Professors see the queue in their analytics dashboard.
  - Approve: is_verified = TRUE on resource, record in moderation_logs,
    uploader gets +15 karma (professor_verify action).
  - Reject: reject_reason saved, resource remains unverified, uploader notified.
  - Verified resources get a "Professor Verified ✅" badge in the UI.

Moderation Actions:
  - Delete Resource: is_deleted = TRUE (soft delete). Resource hidden from students.
  - Restore Resource: is_deleted = FALSE.
  - Flag User: is_flagged = TRUE, flag_reason saved. Flagged users visible to moderators.
  - Restrict User: is_restricted = TRUE. Restricted users cannot upload or post.
  - Delete Discussion: is_deleted = TRUE on discussion.
  All actions logged in moderation_logs with moderator_id, action, target, reason.

14. SECURITY
================================================================================

  JWT Authentication
    - All protected routes require "Authorization: Bearer <token>" header.
    - Tokens are generated by Supabase Auth and validated on each request.
    - Token expiry handled by Supabase (configurable, typically 1 hour).
    - Refresh tokens allow session continuation without re-login.

  Role-Based Access Control (RBAC)
    - role.middleware.js enforces professor-only routes.
    - professor-only: classroom creation, analytics, moderation, verification,
      auto-approving resources, generating AI tests.
    - student-only restrictions: cannot access other students' private data.

  Helmet.js Security Headers
    - Content-Security-Policy (CSP): restricts script/style/font/image/connect sources.
    - HSTS (HTTP Strict Transport Security): enforces HTTPS in production.
    - X-Frame-Options: prevents clickjacking.
    - X-Content-Type-Options: prevents MIME sniffing.
    - Referrer-Policy: controls referrer header leakage.
    - Note: crossOriginEmbedderPolicy is disabled (required for PDF.js).

  Rate Limiting
    - Auth endpoints: 20 requests per 15 minutes per IP.
    - Chat endpoints: 30 messages per minute per user.
    - Prevents brute-force and API abuse.

  Input Validation
    - express-validator validates all request bodies.
    - File type validation via MIME type checking (file-type package).
    - SQL injection prevented by parameterized queries ($1, $2, ...) via pg.
    - No raw string interpolation in SQL queries.

  CORS
    - Restricted to known origins (localhost + CLIENT_URL env var).
    - credentials: true allows cookies/auth headers.

  HTTPS
    - Enforced in production via redirect middleware.
    - Vercel and Render both provide automatic HTTPS certificates.

  Secrets Management
    - .env files never committed (in .gitignore).
    - Production secrets set via Render dashboard / Vercel env vars.
    - Supabase service role key only used server-side (never exposed to browser).
    - Browser uses only the anon/public Supabase key.

18. KNOWN LIMITATIONS & NOTES
================================================================================

  Render Free Tier Cold Starts
    - After 15 minutes of inactivity, the first request takes ~30 seconds.
    - Workaround: Use an uptime monitor (e.g., UptimeRobot) to ping /api/health.
    - Fix: Upgrade to Render's paid plan ($7/month).

  OpenAI Free Credits
    - GPT-3.5-turbo requires a paid OpenAI account or free trial credits.
    - The FAQ fallback works perfectly without any API key.
    - AI test generation REQUIRES an OpenAI key (no fallback for test generation).

  Supabase 50MB File Limit
    - Free tier limits individual file uploads to 50MB.
    - Large PDFs may need to be compressed before upload.
    - Workaround: fileProcessor.js handles compression during upload.

  Neon DB 0.5GB Storage
    - Free tier. Monitor usage via Neon console.
    - Each classroom's resources metadata adds up. Binary files go to Supabase.

  Redis Caching
    - Optional. Without Redis, API responses are not cached.
    - App works fine without it for development and small deployments.
    - Recommended for production with high user counts.

  Email Delivery
    - Gmail may rate-limit high-volume sending.
    - For production, switch to SendGrid, Resend, or Mailgun free tiers.

  Virus Scanning
    - The current fileProcessor.js checks file types but does NOT do real
      antivirus scanning (no ClamAV integration). This is a planned feature.

  Heatmap Performance
    - With 1000+ highlights per page, heatmap calculation may be slow.
    - Caching in heatmap_data table mitigates this.
    - Consider background jobs for recalculation in production.

19. COMMON ERRORS & FIXES
================================================================================

  Error: "Cannot find module '../config/db'"
  Fix: Run npm install in server/

  Error: "Invalid token" on API calls
  Fix: Check JWT_SECRET is set in server/.env

  Error: "CORS error" in browser
  Fix: Check CLIENT_URL in server/.env matches your frontend URL exactly.

  Error: "relation does not exist" (DB error)
  Fix: Run node run-migrations.js in server/

  Error: Chat widget not appearing
  Fix: You must be logged in. ChatWidget renders only inside Layout (authenticated routes).

  Error: OpenAI API key not working
  Fix: Key may be expired or have no credits. Chatbot auto-falls back to FAQ mode.
       Test with GET /api/health — if ai: "rule-based", fallback is active.

  Error: Vitest tests failing
  Fix: Run npm install in client/ to get all testing dependencies.

  Error: Jest tests failing
  Fix: Run npm install in server/ to get Jest + Supertest.

  Error: "File type not supported"
  Fix: Only PDF, DOCX, PPTX, TXT files are accepted.

  Error: Supabase "storage object not found"
  Fix: Run supabase_bucket_setup.sql in Supabase SQL Editor and ensure
       the "resources" bucket is created and set to public.

  Error: "Rate limit exceeded"
  Fix: Auth endpoints: wait 15 minutes. Chat: wait 1 minute.
       In dev, rate limits can be temporarily increased in rateLimit.middleware.js.
